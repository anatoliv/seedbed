Does a tailored prompt beat the raw seed?

Seedbed exists because a prompt shaped for a specific model should beat the short seed. That claim was checked once the tool worked, before this site was written. This page is the method, the scoring and every raw output, so the result can be disagreed with rather than taken on trust.

Method

Four tasks with known right answers. All four are defects that had been diagnosed and fixed in the Seedbed repository the day before, so there is a correct answer rather than a matter of taste. Two are "explain this code" tasks and two are "fix this bug and test" tasks.

Two conditions, same model, same appended input, one call each. Condition A is the raw seed, verbatim: explain what this code does or fix this bug and test. Condition B is that model's render of the same seed, built by Seedbed's enhancer from the vendor's published prompting guidance. The render was built for the model actually under test, not borrowed from another target.

Criteria were registered before anything ran, so the scoring could not be fitted to the results. Explain tasks: (1) names the actual mechanism, (2) invents no behaviour, (3) states what it could not determine rather than guessing. Fix tasks: (4) identifies the true root cause, (5) proposes a fix that would work, (6) includes a test that would fail before and pass after.

Declared deviations. Four tasks rather than the five first planned. Scored against checkable criteria by one reader rather than judged blind. One run per condition at temperature 0. Both fix tasks in the Opus run had swift build and swift test refused by the permission system, so nothing was compiled or run in either condition. That hit the two arms unevenly: the render asks the model to reproduce the failure and run the tests, the seed asks it to verify nothing, and those are the two tasks the render lost. The scoring stands as recorded, and neither task has been re-run with the toolchain available.

Run 1: Claude Opus 5. No correctness advantage.

What the difference consists of

The render stops the model inventing. Condition A produced five confident fabrications on t2 alone. Condition B produced none, and instead said "not shown in the provided code" nine times across the two explain tasks.

The render makes it answer the question that was asked. Both fix tasks asked for a test. A produced none in either. B produced XCTest code both times.

Shorter, not longer. B's answers ran 409, 498, 351 and 319 words against A's 802, 831, 629 and 540: 44% fewer, while scoring higher. The raw seed made this model ramble; the render made it terse and specific. On Opus the render made answers longer and no better.

The task both runs failed, and what it changed in the tool

t4 was lost by the render on both models, in the same condition: a bare snippet, no repository. Every render told the model to reproduce the failure and read the surrounding code before changing anything, which is right for an agent in a checkout. Given a snippet in a chat window, the same render searched for code that was not there and got the answer wrong. The tool was building prompts for one usage context and handing them to another.

The change. A seed now declares where it is pasted, agent or chat. The context goes to the enhancer and is part of the staleness hash, so a render built for one context is stale for the other. The same five-word seed, built both ways:

agent: "Reproduce the failure first. Find the relevant code and tests, then run whatever command demonstrates the bug. Do not change code until you have seen the failure yourself."
chat: "The snippet below is the only material available to you: there is no repository, no test runner, no ability to execute anything. Verify by reasoning, since you cannot run anything. If nothing in the snippet is actually broken, say so instead of manufacturing a fix."

Given t4 as a bare snippet with the chat-context render, Opus 5 found the real cause: performClick sends the button's action to its target, so it re-enters the click handler instead of opening the menu. It also caught the teardown as a secondary issue rather than mistaking it for the cause, and stated its assumptions explicitly. One task, one model, one run: it shows the context field addresses the measured failure, not that chat context is better in general.

What this does and does not settle

  • Settles: tailoring a prompt to a weak model measurably improves its output, mostly by suppressing fabrication and by making it comply with instructions it otherwise ignores. Combined with the flat Opus result: the enhancer earns its cost on weak models and not on strong ones.
  • Does not settle: the weak-model run is one 30B vision-language model, not the 70B text model first planned. One run at temperature 0, scored by one reader, four tasks. The two Opus fix tasks ran with the build and test commands blocked, so half of that null result comes from a setting where the render's instructions could not be followed. A second person reproducing it would be worth more than this page.
  • Not claimed anywhere on this site: that Seedbed saves time (never measured; the tool counts copies, not minutes), that it improves any model (measured false on Opus 5), or that anyone but its author uses it.
