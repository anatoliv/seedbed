## Edge cases and assumptions

The strong precondition is on `_split`: it must return a two-tuple of a mapping and a string, and the mapping must be `.get`-able. Beyond the empty-body check, nothing validates types. That leaves a few sharp edges:

`bool(meta.get("pinned", False))` coerces rather than parses, so a value that arrives as the string `"false"` — which is what a naive frontmatter parser might hand back — becomes `True`. Whether that can happen depends entirely on `_split`.

More likely to bite: `list(...)` on `targets` and `tags` assumes an iterable of strings. If the file writes `targets: gpt-4` as a scalar instead of a list, `list("gpt-4")` silently produces `['g', 'p', 't', '-', '4']` rather than failing. That's the one spot I'd call a latent bug, and again it hinges on whether `_split` normalises scalars to lists.

Finally, a Python subtlety: defining a property named `hash` does not make `Seed` hashable. A `@dataclass` with the default `eq=True` sets `__hash__ = None`, so `Seed` instances can't go in a `set` or serve as dict keys — you have to key on `seed.hash` explicitly, which is presumably the intent given the render-cache framing.
